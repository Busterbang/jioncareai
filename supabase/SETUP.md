# Supabase setup

The project SQL migration is at `migrations/20261027000000_jointcare_initial_schema.sql` and defines the eight requested JointCare tables plus `trusted_emergency_contacts`, with UUID foreign keys, timestamps, checks, indexes, triggers and RLS policies. The contact table has patient-only row policies and no clinician policy. `seed.sql` is intentionally a no-op, so synthetic examples cannot enter real accounts.

**This task does not apply migrations to the remote Supabase project.** Review the SQL and inspect/backup the target schema first, especially if any of these table names already exist. For a new setup, run `migrations/20261027000000_jointcare_initial_schema.sql` first and `migrations/20261027010000_jointcare_existing_user_profile_backfill.sql` second through the Supabase SQL Editor or your normal versioned migration pipeline. If the initial migration has already been applied, run only the follow-up profile-backfill migration. It is idempotent: it inserts a missing profile as `patient`, does not overwrite an existing profile or operator-managed role, and does not trust Auth metadata for privileged roles. This repairs missing profile rows for users who registered before the signup trigger was installed. Validate behavior with synthetic test users in a non-production environment before adding patient data.

New users are assigned the `patient` role by an Auth insert trigger; client metadata cannot assign a privileged role. A trusted project administrator must verify a clinician account, promote its `profiles.role` through the operator path and insert the explicit `clinician_patient_access` mapping. Remove or expire the mapping to revoke access. The application UI cannot grant assignments.

RLS permits patients to see their own permitted settings, sessions and symptoms, plus their own sensor/analysis records; clinician reads require an active explicit mapping. Session writes and trusted-contact access require the signed-in owner to have the patient role; trusted contacts have no assigned-clinician read policy. Device inventory, sensor ingestion and rule-generated analysis have no authenticated-client write policies. Those privileged operations use the protected FastAPI service-role client. Never expose the service-role key in frontend assets, the public environment, logs or firmware.

Set the Supabase Auth Site URL/redirect allowlist to the real deployed app origin and any local/Preview origins. Password-recovery redirects use `/#/login`. Check email confirmation settings so sign-up and recovery match your chosen policy.

All synthetic demo content is local browser state or a disabled-by-default API sample response and is never seeded into these tables. `DATABASE_URL` is optional documentation only; the current backend accesses Supabase through its REST/Auth API.
