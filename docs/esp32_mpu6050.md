# ESP32 + MPU6050 hardware guide

This sketch streams sensor measurements to the **deployed** JointCare API for an active patient session. It is a motion logger example, not a medical device. The MPU6050 measures acceleration and angular velocity; it does not detect inflammation, confirm a diagnosis or establish clinical range of motion.

## Before hardware setup

1. Set up the Supabase schema manually using `supabase/SETUP.md`, configure the required protected environment values, publish the app, and verify an account in a **non-production** test project. This repository did not apply the SQL migration or verify a remote Supabase service.
2. Sign in as a patient and open Monitoring → **Real hardware**. Enroll a device using the identifier you want to use for `DEVICE_ID`; copy the one-time token immediately to your local untracked firmware settings. The raw token is not retrievable later.
3. Select that device and start a real session in the dashboard. Copy the **Active session ID** shown by the app to `SESSION_ID`. This creates the authorized device/session association required before samples can be accepted.
4. Publish to an HTTPS host and set `API_BASE_URL` in the firmware to the deployed application origin only (for example, `https://your-jointcare-host.example`, without `/api/v1`). Preview's internal port is not a public device endpoint.
5. Copy `firmware/esp32_mpu6050/secrets.example.h` to `secrets.h` in the same sketch folder; replace Wi-Fi, `DEVICE_TOKEN`, `DEVICE_ID`, `SESSION_ID`, API URL and TLS root CA locally. `.gitignore` excludes `secrets.h`. Never commit/share it or put the Supabase service-role key in firmware.

The dashboard starts/pauses/resumes/stops the database session. The board only sends batches to `POST /api/v1/sensor/devices/ingest`; it cannot create or stop patient sessions by itself. After sending a final batch, send `s` in Serial Monitor to stop local transmission, then click **Stop session** in the dashboard. If the dashboard session is stopped first, the server correctly rejects later samples.

## Wiring map — verify the exact board and breakout

| MPU6050 breakout | ESP32 |
| --- | --- |
| SDA | Configured `I2C_SDA_PIN` (default GPIO 21; verify your exact board) |
| SCL | Configured `I2C_SCL_PIN` (default GPIO 22; verify your exact board) |
| GND | Common ESP32 ground |
| VCC | Only a supply voltage explicitly supported by that exact breakout |
| AD0 (if present) | GND generally selects I²C address `0x68`; logic-high may select `0x69` |

**Power off while wiring. Board pins, logic voltage, regulator and I²C pull-up levels depend on the exact ESP32 board and MPU6050 breakout. Check both manufacturers' electrical specifications; never assume a breakout accepts 5 V or has ESP32-safe 3.3 V I²C pull-ups.** Use appropriate protected low-voltage power, secure connections, and avoid pins that are reserved/input-only on your board.

## Compile and configure

- Select and verify the exact ESP32 board/port in Arduino IDE or Arduino CLI.
- Install Arduino ESP32 core, Adafruit MPU6050, Adafruit Unified Sensor and ArduinoJson v6 libraries.
- Set the matching `I2C_SDA_PIN` / `I2C_SCL_PIN`, a conservative `SAMPLE_RATE_HZ` from 1–25 Hz (default 10), and batch size 1–100 (default 20).
- Set calibration count (default 100 samples) and `FILTER_ALPHA` (0–1; lower smooths more and lags more). Hold the module still in the intended Z-up reference orientation during startup calibration.
- Configure `API_ROOT_CA` with the appropriate trusted root/intermediate certificate for the public deployed TLS chain. The firmware validates the server certificate; do not turn verification off. Keep the device clock synchronized: the sketch obtains UTC through NTP and will not transmit until a usable UTC clock is available.
- Upload, then open Serial Monitor at 115200 baud. The sketch prints device/session labels and network/sensor status; it does not print the token.

## Data contract

At 10 Hz and a 20-reading batch, the sketch attempts a batch about every two seconds. It sends timezone-aware UTC `measured_at`, `accel_x/y/z` in m/s², `gyro_x/y/z` in rad/s, and a relative accelerometer pitch in degrees. The relative value is calculated against the single stationary startup orientation and is not a calibrated joint range. The token is sent over HTTPS in the request body and Authorization header; the backend verifies its digest, associated active device and active session before writing to Supabase.

On transient failure, a batch up to `BATCH_SIZE` is kept in RAM and retried with exponential backoff up to 60 seconds. The buffer is bounded and **not durable**: samples can be dropped if power is removed, time is lost, a batch cannot be sent, or the server rejects the session/token. The board does not currently persist a queue across reboot. Ingest is capped by the backend and gateway; do not raise sample rates without capacity/safety review.

## Manual hardware validation checklist

- [ ] Identify board and breakout; verify supply, pinout, I/O logic, pull-ups and I²C address before powering.
- [ ] Wire with power off; check common ground, SDA/SCL, correct pin macros and absence of shorts.
- [ ] Confirm no abnormal heat, smoke, odor or unstable connection at low-voltage power.
- [ ] Confirm MPU6050 initializes and remains still through the stationary calibration step.
- [ ] Rotate the sensor gently and confirm values change plausibly and return near the reference orientation; this checks function, not calibration accuracy.
- [ ] Confirm UTC synchronization, Wi-Fi connection and CA-validated HTTPS.
- [ ] Enroll a synthetic test device, start a synthetic-account session, and inspect one accepted batch and its timestamps in the test Supabase project.
- [ ] Disconnect/reconnect Wi-Fi and verify status/backoff; confirm only a bounded in-RAM batch is retried.
- [ ] Send `s` to stop local transmission, then stop the session in the app; verify subsequent writes are rejected.
- [ ] Revoke/disable test device credentials when finished.

**No physical ESP32/MPU6050, deployed endpoint, remote migration or remote Supabase RLS execution was available for verification in this task. Complete and record the manual checks before any real health-related use.**

## Troubleshooting

| Symptom | Check |
| --- | --- |
| `secrets.h` missing | Copy the example to `secrets.h` next to the `.ino` and fill it locally. |
| Invalid config serial message | Check Wi-Fi SSID, HTTPS origin, one-time token, active session ID, CA, and that placeholders were replaced. |
| MPU6050 not found | Power off; confirm common GND, exact configured SDA/SCL, address `0x68`/`0x69`, pull-ups and supported supply. |
| UTC clock unavailable | Check Wi-Fi and whether the network permits NTP (`pool.ntp.org` or `time.nist.gov`); no samples are sent without timezone-aware time. |
| TLS handshake fails | Check the deployed origin, trusted CA chain, board clock and PEM escaping. Never disable certificate validation. |
| HTTP 401/403 | Check that the device token is current and that its device is active and the same dashboard session is still active and linked to that device. Revoke/re-enroll an exposed token. |
| HTTP 404 | Check the public HTTPS origin and exact path `/api/v1/sensor/devices/ingest` (no manual trailing slash). |
| HTTP 413/422 | Inspect batch size, exact field names, timezone in `measured_at`, axis bounds and JSON size. |
| Batch retries remain | Check server readiness, account/session state, token, TLS, body and rate limits. Failed batches remain only in RAM and may be lost on reboot. |
| UI shows no recent data | Refresh the authorized dashboard records, confirm `session_id` matches the active device session, and check backend/API status. |
